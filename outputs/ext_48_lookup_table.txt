  **THE PRECONDITION IT RELAXES.**  Section 12.16 requires `log z(x)` to be LINEAR in
  a fixed FINITE basis of `x`.  A table requires something DIFFERENT and WIDER: the
  source must be a FIXED function of ONE SCALAR,

      z = T(u),   u = ||(x - c)/h||^2,

  because then a single 1-D table serves every particle and every width.  The table's
  entries are what a calibration would MEASURE from the device -- which is why this
  belongs in the device and not in the trainer, where `features()` forbids it.

  **AND WHAT IT DOES NOT ADMIT, STATED BEFORE ANY RESULT.**  Yukawa's `exp(-r)/r` is
  NOT of that form: its SHAPE depends on `h`, so one table of `u` cannot carry it.
  The honest claim is 'any kernel that is a FIXED function of `u`' -- wider than 'any
  polynomial exponent', narrower than 'any kernel'.

====================================================================================================
  P4  the payoff: a source the CLOSED-FORM operator cannot treat
====================================================================================================

  `T(u) = exp(-sqrt(u))` is the exponential (Laplace) kernel `exp(-||x-c||/h)`, whose
  `log z = -||x-c||/h` is a CONE.  No fixed finite basis of POLYNOMIALS in `x`
  represents it, so 12.16 excludes it and the closed-form geometry operator cannot be
  applied.  **The operator's own residual is what proves that half.**

  source                                          log_rms                    verdict
  ------------------------------------------------------------------------------------
  Gaussian (in the closed-form class)           3.212e-06             fits the basis
  Laplace (NOT in the class)                    7.132e-02      REJECTED by the basis

  **So the residual says the Laplace source is not a node of the Gaussian family --
  which is a TRUE statement about the closed-form operator and NOT a failure of the
  device.**  The table computes that source exactly (P1's law covers it), so what the
  table changes is which sources the FORWARD can realise, and it does that without
  pretending the closed-form operator now covers them.

====================================================================================================
  P5  VERDICT
====================================================================================================

  P1's measured error is AT MOST `(du)^2/8` and approaches it from below as M grows
  (ratio 0.445 at M=8 to 0.987 at M=512).  **The ratio is
  below 1 at small M because the sample points do not sit at the worst-case midpoint of
  an interval** -- so `(du)^2/8` is an UPPER BOUND on the error, which is the useful
  direction: a table size can be CHOSEN from it rather than tuned.

  P2: the suite flags 3 of 3 tabulated sources through `log_rms` ALONE,
  with no new code -- `node_from_response` already reported the number that matters.

  **WHAT THE TABLE ACTUALLY BUYS, AND IT IS NOT SPEED.**  A measured 2x slowdown in
  `features()` is irrelevant because **the project's cost unit is MEASUREMENTS**, so it
  cannot change any published conclusion.  What it buys is REACH: the forward of any
  source that is a FIXED function of one scalar, which is a wider class than the
  polynomial exponents 12.16 admits -- and the table's entries are what a calibration
  would MEASURE, so this is a device change rather than a formula.

  **AND THE LIMITS, WITH THE FIRST ONE UP FRONT.**  Yukawa's `exp(-r)/r` is NOT covered:
  its shape depends on `h`, so a single table of `u` cannot carry it and `h` would have
  to index a family of tables.  The class is 'fixed functions of `u`', not 'any kernel'.
  The table is also a 1-D approximation, so its error enters the FORWARD and not the
  operators, and a source whose `log z` is non-polynomial still needs a different
  recovery than the closed-form one -- the table makes it computable, not solvable.
