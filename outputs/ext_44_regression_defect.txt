  `ext_43` found the deep regression path at end-to-end `R^2 ~ 0` while its per-layer
  readout solved to `~0.34-0.38`.  So the readout is not the bottleneck and the
  question is what is.  **The code answers it, and the answer is a discrepancy:**

      training:   pred_i = _proto_predict(h_i, y_proto_i, h_proto_i)
                  acc     = acc + pred_i          (running sum, layer by layer)
                  layers 2/3 are trained on `y - acc`
                  # 'At predict time these are summed -> recovers original y'

      predict:    return (h_last_A + h_last_B) / 2

  **`predict` returns the LAST LAYER'S OUTPUT, which is a RESIDUAL, not the target**
  -- and its own docstring says the opposite ('proto-weighted prediction with residual
  accumulation.  output = (acc_A + acc_B) / 2').  **Code and docstring disagree.**

  AND IT IS TESTABLE WITHOUT EDITING THE BASE: `train` stores the prototypes on the
  trainer and `_proto_predict` is a method, so the prediction the TRAINING path was
  built around can be replayed here.

  a calibration cannot repair a broken prediction path, AND on the repaired path it
  is not the thing that helps.

  **CONSEQUENCE, stated because it is the point of the whole exercise:**
  `himal_nd`'s regression mode is used by `nd_09` (a SPEED benchmark) and by

  published number depends on** -- which is why it survived -- **and it would
  have corrupted the first serious use of that path.**

  **THE HONEST LIMITS.**  The replay reconstructs the intended prediction from the
