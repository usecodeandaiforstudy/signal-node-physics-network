  Section 11 item 4 asks for a genuine `m > 1` setting and suggests 'the repository's
  4D classification task'.  **Half A's readout is `W = C . W_g` with `C` of shape
  `m x k`, so `rank(W) <= min(m, k)` -- the constraint bites only when `k < m`.**
  The arithmetic is checked below rather than asserted, and it decides whether the
  suggested task can host the test at all.

====================================================================================================
  P1/P2  the repository's classification tasks: what m is, and can the test bite?
====================================================================================================

  task                        classes   m  rank(W)  eff rank        k=1        k=2        k=3   max |gap|
  ------------------------------------------------------------------------------------------------------------
  moons (base, 2-class)             2   2        1         1  -1.62e-05  -1.64e-05  -1.64e-05    1.64e-05
  4d moons (nd_01, 2-class)         2   2        1         1  -8.59e-08  -8.78e-09  -8.78e-09    8.59e-08

  **THE PREDICTION HELD, AND IT IS STRONGER THAN EXPECTED.**  At `m = 2` the
  constraint is empty for every `k >= 2` -- and the measured `rank(W)` is **1**, not
  2, because the target is centred so the two one-hot channels are complementary.
  **So even `k = 1` is already full rank there.**  The residual gaps are NOT
  floating-point zero -- they are ~1e-5, the ALTERNATING LEAST SQUARES
  convergence floor rather than a rank effect: at `k` at or above the effective
  rank the rank-k model class CONTAINS the full-rank fit.

  task                         gap at 60 iters   gap at 400 iters   shrinks?
  --------------------------------------------------------------------------
  moons (base, 2-class)              -1.64e-05          -1.21e-06       True
  4d moons (nd_01, 2-class)          -8.78e-09          -7.94e-09       True

  **AND IT SHRINKS WITH MORE ITERATIONS, which is what makes it the optimiser's
  floor and not the constraint's.**  That is three orders of magnitude below any
  effect half A is about.**  **The task item 4 proposes would produce a VACUOUS test of
  half A, in the same way `train_01` was vacuous** -- and the check that would have
  caught it is the effective-rank column, which is why it is in the table.

====================================================================================================
  VERDICT: what item 4 should have said
====================================================================================================

  **THE ITEM'S CONCLUSION IS RIGHT AND ITS EXAMPLE IS WRONG.**  Half A does rest on
  a synthetic multi-output target, and a real one is worth having -- but the task
  the item names cannot supply it, because at `m = 2` the rank constraint is empty
  for every `k >= 2`, which is exactly the range half A's boundary lives in
  (`k = 3` works, `k = 2` fails).  **Running the test there would have produced a
  vacuous pass, of the same kind as `train_01`'s.**

  The repository DOES have a genuine `m >= 3` setting -- its own cached CIFAR-10
  five-class task, which its own CIFAR scripts use -- so the item should point
  there.  That is what P3 runs.

  **AND ONE THING THIS SETTLES ABOUT THE SYNTHETIC TARGET.**  `ext_02`'s `m = 8` was
  not a convenience: it is what makes the constraint bite at `k = 3`.  A synthetic
  target with a real `m` is the CORRECT instrument for a question about rank, and
  the item's framing -- that the synthetic target is the weakness -- inverts that.
