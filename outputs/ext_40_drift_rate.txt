  Section 11 item 6 asks how often a deployment must re-measure, and says the answer
  is set by 'the drift it expects'.

  **THERE ARE TWO DRIFT CHANNELS HERE AND THE ITEM NAMES THE WRONG ONE.**  The base
  version's own docstring separates them:

      mismatch -> perturbs h (differential_pair gain) and the MVM gain  = GEOMETRY
      drift    -> multiplies memristor conductances W                   = WEIGHT-only

  and `physical_simulator/components.py` implements the first literally:

      L80  # Gain mismatch: each channel's h has independent deviation
      L81  h_noisy = h * (1 + np.random.normal(0, mismatch_std, h.shape))

  A PLACEMENT correction is a WIDTH correction, so the channel that makes it stale is
  `mismatch`.  `ext_15` drifted the WIDTHS (`w * (1 + drift)`) while calling it
  'drift', so it exercised the mismatch channel's effect under the other channel's
  name.  **That is a naming defect in item 6, not in ext_15's measurement.**

====================================================================================================
  P1  the RATE semantics of the two channels
====================================================================================================

  `drift`      `components.py`: 'Conductance drift standard deviation (per read
               operation)' -- drawn FRESH ON EVERY FORWARD CALL, so it HAS a rate,
               and the rate is per READ.
  `mismatch`   `h_noisy = h * (1 + np.random.normal(...))` -- ONE draw, no time axis,
               so it has NO rate at all in this model.

  the base version's shipped device levels (drift, mismatch):
      abl_ideal    drift 0          mismatch 0         
      high         drift 0.005      mismatch 0.05      
      low          drift 0.0005     mismatch 0.01      
      medium       drift 0.001      mismatch 0.02      
      none         drift 0          mismatch 0         

  **SO A RE-MEASUREMENT INTERVAL IN READS CAN BE DERIVED FOR THE WEIGHT CHANNEL AND
  CANNOT BE DERIVED FOR THE GEOMETRY CHANNEL.**  P2 measures what both need -- the
  tolerance -- and P3 converts it for the channel that has a rate.

====================================================================================================

====================================================================================================
  P3  the WEIGHT channel: a tolerance that CAN be converted to an interval
====================================================================================================

  **THE WIDTH TOLERANCE ABOVE CANNOT BE CONVERTED, and dividing it by the `drift`
  rate would be the very conflation this script is about** -- `d*` is a GEOMETRY
  quantity and `drift` perturbs WEIGHTS.  An earlier draft of this section did
  exactly that division; it is recorded rather than quietly dropped.

  So the weight channel needs its own tolerance, measured the same way: perturb the
  readout weights and find where the calibrated arm falls to the **project's own 0.05
  learning floor** (`ext_37` uses the same bar), which is a criterion the repository
  already owns rather than one invented here.

  **THE PERTURBATION IS PER-WEIGHT AND RANDOM, WHICH IS WHAT THE DEVICE DOES.**  The
  model draws `normal(0, std, (n_out, n_in))` -- an independent deviation per
  conductance -- and it happens AFTER the calibration, so the structure is ext_15's:
  fit on clean features, then perturb the weights, then score.  **An earlier draft
  scaled the whole feature matrix by `(1 + delta)` and got a FLAT curve at every
  `delta`, because a uniform scaling is absorbed exactly by ridge** -- the flatness
  was the tell, and the tolerance it reported was meaningless.

  task       +0.000   +0.050   +0.100   +0.200   +0.400   +0.800
  ----------------------------------------------------------------
  4d         +0.576   +0.573   +0.567   +0.547   +0.472   +0.190
  steps      +0.157   +0.145   +0.128   +0.084   -0.049   -0.499

  **THE WEIGHT TOLERANCE IS d*_w = 0.20** -- the largest per-weight
  relative deviation the calibrated readout still survives above the 0.05
  floor, taken as the binding one across tasks.

  For the WEIGHT channel the model's semantics give the bridge directly: if each
  read contributes an independent deviation of magnitude `sigma`, an accumulated
  drift after `N` reads has magnitude `sigma * sqrt(N)`, so

      N* = (d*_w / sigma)^2   reads

  with d*_w = 0.20, and sigma the base version's own shipped drift values:

  device level    drift sigma       N* (reads)  mismatch sigma   placement interval
  ----------------------------------------------------------------------------------
  abl_ideal                 0            never               0        NOT DERIVABLE
  high                  0.005            1,600            0.05        NOT DERIVABLE
  low                  0.0005          160,000            0.01        NOT DERIVABLE
  medium                0.001           40,000            0.02        NOT DERIVABLE
  none                      0            never               0        NOT DERIVABLE

  **THE LAST COLUMN IS THE ANSWER TO ITEM 6 AND IT IS NOT A NUMBER.**  A placement
  correction's staleness is set by the GEOMETRY channel, `mismatch` -- and that
  channel is drawn ONCE, with no time axis, so the repository cannot express a rate
  for it.  **A re-measurement interval for a placement correction therefore cannot be
  derived from this model at all**, which is a sharper statement than 'no measurement
  here sets that number'.

====================================================================================================
  P4  VERDICT: what item 6 should say
====================================================================================================

  **1. THE CHANNEL.**  Item 6 says 'the drift RATE' for a PLACEMENT correction; the
  channel that perturbs a width is `mismatch`, and `ext_15` drifted widths under the
  name 'drift'.  The item should say GEOMETRY drift, and the base's own docstring is
  where the distinction is written down.

  **2. THE TEST NOW REGISTERS ON BOTH SIDES** (2 of
  2 tasks help in both directions).  `ext_15` reported that its score
  could not register the drift because the plan preferred wider widths; sweeping both
  signs removed that, and **d* = 0.10 is the number item 6 was missing** -- it is a
  property of the plan and the task, not of the device.

  **3. THE INTERVAL EXISTS FOR THE WEIGHT CHANNEL AND ONLY THERE.**  `N* =
  (d*_w/sigma)^2` with `d*_w = 0.20` is available because `drift` is drawn per read,
  and the table gives it for the shipped device levels.  **For a placement correction
  the repository cannot supply an interval**: its channel is `mismatch`, which is drawn
  once, and **the geometry tolerance measured in P2 must NOT be divided by the weight
  rate** -- the missing piece is a bias-current drift law, not a measurement.

  **THE ASSUMPTIONS, stated because the bridge is an assumption and not a
  measurement:** the random-walk accumulation `sigma*sqrt(N)` is the standard
  memristor picture, and the model's own semantics are I.I.D. PER READ rather than
  cumulative -- so under the model as written the correction is stale on EVERY read
  and 'how often to re-measure' does not arise.  **The interval is what a cumulative
  device would need, computed from a tolerance this repository did measure.**  A
  wall-clock interval additionally needs a read rate, which is a device property.
